## Scope & method (что прочитано, что запущено)

`schema_name` из `postgres.py` подтверждать/аллоуклистить" я сознательно не трогаю — это вопрос
security, не производительности; я лишь подтверждаю, что f-string-интерполяция схемы сама по себе
не создаёт измеримых накладных расходов (это просто конкатенация строки перед каждым запросом).

## Findings

### 1. [High] `compute_ranking` пересчитывает ранжирование по ВСЕМ накопленным строкам на каждом раунде + ещё раз в конце

**File:Line**: `src/llm_bench/runner/round_runner.py:122-128`, `src/llm_bench/runner/benchmark.py:288-295`,
`src/llm_bench/ranking/ranker.py:120-165` (в частности стрим на строке 161:
`async for row in storage.query_rows(experiment_tag=experiment_tag):`)

**Описание**: `run_round()` после `asyncio.gather(...)` по всем парам раунда вызывает
`compute_ranking(cfg.storage, cfg.experiment_tag, ...)` **без фильтра по раунду** —
`query_rows(experiment_tag=...)` (`ranker.py:161`) стримит вообще все строки, когда-либо записанные
под этим `experiment_tag`, включая строки всех предыдущих раундов того же прогона (`RunRow` вообще не
имеет поля `round_idx` — см. `core/types.py:174-232` — так что инкрементальный фильтр "только новые
строки" технически невозможен без изменения схемы). Это вызывается **на каждом раунде** каскада, а
затем `Benchmark.run_phase` (`benchmark.py:288-295`) вызывает `compute_ranking` **ещё раз** в конце,
уже над полным набором строк финального раунда — то есть строки последнего (самого большого) раунда
обсчитываются дважды подряд.

Для дефолтного расписания `HalvingSchedule(round_sizes=(52,26,13,7), units_per_arm=(4,8,12,12))`
(halving/schedule.py:23-27) число вызовов пары `(model,unit)` на раунд — 208/208/156/84 (см.
`total_calls_for_stage`). Если считать по одному "кластеру строк" (по одной стадии), суммарное число
"row-scorer-проходов" по всем round-барьерам получается:
208 (round1) + 416 (round2, т.к. round1+round2) + 572 (round3) + 656 (round4) + 656 (final) = 2508,
против идеального 656 — то есть **~3.8x избыточных вызовов `row_scorer`/`GoldChecker.score()`** и
~3.8x избыточных полных чтений storage на весь прогон.

**Why it matters / сценарий отказа**: `default_row_scorer` (`ranker.py:59-70`) сам по себе дешёвый,
но framework явно спроектирован под подключаемые дорогие скореры — докстринг `compute_ranking`
(`ranker.py:9-20`) прямо говорит про VocabApp'овский `richness_accuracy_combo` и опциональный async
`GoldChecker.score()` ("each row is also scored against ground truth", `ranker.py:17-20`), который
может делать собственный I/O. Каждый лишний проход — это не только лишний CPU для скоринга, но и лишнее
полное чтение storage: для `FileStorage` это полный построчный парс `results.jsonl` под глобальным
локом (`file.py:236-269`, см. также находку #6/#7), для `PostgresStorage` — полный `SELECT` по индексу
`experiment_tag` с последующей агрегацией всех совпавших строк в Python-словари
(`_record_to_row` на каждую строку, `postgres.py:319-334`). При 60-100 кандидатах x N unit'ов x M
стадий (заявленный в README масштаб, `README.md:13`) и тысячах вызовов LLM это заметная доля
"собственных накладных расходов фреймворка", которых README прямо обещает избегать.

**Recommendation**: Либо (а) добавить `round_idx`/monotonic offset в `RunRow`/storage-протокол и
считать `compute_ranking` инкрементально (кэшировать агрегаты прошлого раунда, домешивать только новые
строки), либо (б) держать в оперативной памяти раннера собственный累累 running-aggregate
(`scores_by_model`/`cost_by_model`/...), обновляемый прямо в `_run_pipeline` по мере записи каждой
строки, вместо повторного re-streaming всего storage. Финальный вызов в `benchmark.py:288-295` в любом
случае может переиспользовать `RankingReport` последнего раунда, если раунд уже покрывал весь пул
юнитов (частый случай для последнего раунда) — как минимум устранить двойной проход по одному и тому
же набору строк.

### 2. [High] `mad_bootstrap_prune`: пересчёт одного и того же bootstrap-ресэмпла отдельно на каждого кандидата

**File:Line**: `src/llm_bench/halving/pruner.py:159-192` (обе ветки — paired на 159-178 и legacy-fallback
на 181-192), вызов из `src/llm_bench/halving/driver.py:130`

**Описание**: `Halving.promote()` вызывает `mad_bootstrap_prune(scores)` **без** `per_task_unit_scores`
и без `eff_cost` (`driver.py:130` — ни один из этих keyword-аргументов не передаётся), поэтому в
реальной работе фреймворка всегда исполняется ветка "Fallback: legacy unpaired bootstrap"
(`pruner.py:180-192`):

```python
for model, v in eff_items:
    fallback_deviations: list[float] = []
    for _ in range(n_bootstrap):
        resample = [rng.choice(values) for _ in range(n)]
        fallback_deviations.append(v - statistics.median(resample))
    ...
```

`values` — список эффективных очков **всех** кандидатов сразу, общий для всех. `resample` —
IID-выборка из этого общего списка, **не зависящая** от того, для какого именно `model` мы сейчас
считаем нижнюю доверительную границу. То есть один и тот же набор из `n_bootstrap=1000` ресэмплов +
их медиан пересчитывается **заново для каждого из n кандидатов**, хотя единственное, что реально
зависит от кандидата — это вычитаемое `v`. Итоговая сложность — O(n² · n_bootstrap · log n) вместо
достижимой O(n · log n · n_bootstrap) (посчитать 1000 медиан один раз, затем для каждого кандидата
просто вычесть `v`).

Тот же корневой паттерн (пересчёт общей для всех кандидатов величины внутри per-кандидатного цикла)
присутствует и во второй, "paired"-ветке (`pruner.py:159-178`): для каждого `(model, bootstrap-iter)`
заново тянется свежий `idx` и заново пересчитывается `peer_means_eff` по **всем** пирам —
O(n² · n_bootstrap · unit_count). Эта ветка сейчас не задействована из `driver.py` (там
`per_task_unit_scores` не передаётся), но `mad_bootstrap_prune` — публичная API-функция
(экспортируется из `llm_bench/__init__.py:38` и `halving/__init__.py:20,27`), и докстринг модуля
(`pruner.py:56-61`) явно описывает её как "мигрировавшую из VocabApp" логику для консьюмеров, которые
как раз передают per-task-unit-разбивку — так что у этой ветки есть реальный шанс попасть в горячий
путь у внешнего потребителя.

**Измерено** (`bench_pruner.py`, точный вызов как в `driver.py:130`, дефолтные `n_bootstrap=1000`):

| n кандидатов | время |
|---|---|
| 13 | 64.7 мс |
| 26 | 255.8 мс |
| 52 (round 1 по умолчанию) | 986.0 мс |
| 100 (верхняя граница README "60-100 candidates") | 6378.8 мс |

Рост явно超线性 (примерно x4 на удвоение n при малых n, доходя почти до x6.5 на переходе 52→100) —
согласуется с ожидаемой O(n² log n) сложностью, а не с линейной/линейно-логарифмической.

**Why it matters / сценарий отказа**: `promote()` вызывается синхронно между раундами, **до** старта
следующего раунда — то есть событийный цикл в этот момент ничем другим не занят (это естественный
барьер, не конкурирует с in-flight LLM-вызовами), так что это не "зависание" в привычном смысле, а
чистый, полностью устранимый overhead. Но при заявленном в README верхнем масштабе (100 кандидатов)
это уже больше 6 секунд синхронного CPU-bound Python-кода на каждый вызов `promote()` — и рост
квадратичный, так что любое расширение `round_sizes[0]` за пределы 100 (а фреймворк это никак не
ограничивает) быстро уводит время в счёт десятков секунд/минут на один-единственный вызов статистики,
что прямо противоречит заявленной цели "накладные расходы фреймворка должны быть пренебрежимо малы
рядом с LLM-вызовами".

**Recommendation**: В обеих ветках вынести генерацию `n_bootstrap` ресэмплов/медиан **за пределы**
цикла по кандидатам — посчитать один раз список из 1000 медиан (или, в paired-ветке, один раз посчитать
`peer_means_eff`/`median(peer_means_eff)` для каждой из 1000 итераций), затем для каждого кандидата
только вычесть его `v`/`m_pen`. Это убирает множитель `n` из сложности практически бесплатно (тот же
результат, просто без повторной работы) и даёт ожидаемое ~n-кратное ускорение (при n=52 — заметно
меньше секунды вместо ~1 с; при n=100 — доли секунды вместо ~6.4 с). Как более радикальный вариант —
NumPy для векторизации `rng.choice`/`median` по всем ресэмплам сразу, но NumPy сейчас не входит в
зависимости пакета (проверено — `pyproject.toml` его не упоминает), так что чисто-Python хойстинг
ресэмплов — самый дешёвый фикс без добавления новой зависимости.

### 3. [High] `BudgetGate.check()` заново агрегирует весь потраченный бюджет из storage перед КАЖДЫМ вызовом стадии

**File:Line**: `src/llm_bench/runner/budget.py:49-73` (метод `check`), вызов из
`src/llm_bench/runner/round_runner.py:202-207`; агрегация в `src/llm_bench/storage/file.py:287-294`
и `src/llm_bench/storage/postgres.py:365-373` (`query_spend_by_op` → `query_spend_by_stage`)

**Описание**: `_run_pipeline()` перед каждым LLM-вызовом стадии, если задан `cfg.budget_gate`, делает:

```python
if cfg.budget_gate is not None:
    ok, _spent, _cap = await cfg.budget_gate.check(cfg.storage, cfg.experiment_tag, stage.op)
```

`BudgetGate.check()` (`budget.py:60-73`), если для этого `op` задан бюджет
(`self.budgets_by_op.get(op)` не `None`), выполняет `await storage.query_spend_by_op(experiment_tag=...)`
— **полную агрегацию расходов по ВСЕМ уже записанным строкам эксперимента**, каждый раз заново, вместо
инкрементального счётчика. Показательно, что класс уже и так хранит инкрементальное состояние —
`last_call_cost_by_op` (`budget.py:46`, обновляется в `record_cost` на строке 75-79) — то есть
архитектурно инкрементальный трекинг суммарного расхода уже наполовину сделан, просто не для самой
суммы, а только для "стоимости последнего вызова".

Это вызывается один раз **на каждый (model, task_unit, stage) вызов**, для которого сконфигурирован
бюджет по данному `op` — то есть потенциально сотни-тысячи раз за прогон (halving-раунды дают до ~656
пар на стадию при дефолтном расписании, помноженные на число стадий с бюджетом).

**Измерено** (`bench_budget.py`, `FileStorage`, один `op` с бюджетом, растущий тег):

| строк уже записано | время `check()` |
|---|---|
| 0 | 0.17 мс |
| 200 | 19.05 мс |
| 500 | 28.33 мс |
| 1000 | 60.62 мс |
| 1500 | 58.76 мс |
| 1999 | 119.38 мс |

Рост практически линеен по числу накопленных строк — то есть суммарные накладные расходы `check()`
за весь прогон растут квадратично по числу вызовов бюджетируемой стадии (интеграл линейно растущей
функции). Для FileStorage причина в том, что `query_spend_by_op` идёт через `query_rows()`
(`file.py:287-294` → `236-269`), который читает и построчно парсит **весь** `results.jsonl` тега на
каждый вызов (см. также находку #6). Для `PostgresStorage` картина мягче (запрос идёт по индексируемому
`experiment_tag`, `postgres.py:349-363`), но принцип тот же — полная агрегация с нуля на каждый вызов
вместо переиспользования уже посчитанного.

**Why it matters / сценарий отказа**: В отличие от находки #1/#2 (которые срабатывают на естественных
барьерах между раундами), `check()` вызывается **изнутри** конкурентного `asyncio.gather` по парам
раунда (`round_runner.py:105-119`) — то есть в момент, когда несколько пайплайнов для разных
(model, task_unit) работают параллельно. Для `FileStorage` полный скан файла в `query_rows` идёт под
общим `asyncio.Lock` (`file.py:74`, захватывается на 245), а этот же лок захватывают и `record_call`
(`file.py:138`), и `prefetch`/`upsert_prompts` — то есть пока один пайплайн выполняет "дорогой"
budget-check на растущем файле, **все остальные** конкурентные пайплайны, которым в этот момент нужно
записать свою строку или обновить индекс, блокируются на том же локе. Это прямо противоречит замыслу
`global_concurrency=30`/`per_op_concurrency` — часть заявленного параллелизма фактически схлопывается
в последовательное I/O в моменты, когда включён `BudgetGate` (а это ровно тот сценарий, для которого
`BudgetGate` и существует — докстринг явно ссылается на "VocabApp's Phase 1 $20 budget envelope",
`budget.py:5-10`).

**Recommendation**: Хранить в `BudgetGate` (или в `RoundConfig`) инкрементальный `spent_by_op: dict[str,
float]`, инициализируемый один раз (одним запросом к storage) при старте прогона/раунда, и обновляемый
в памяти внутри `record_cost()` вместо повторного полного запроса на каждый `check()`. Это убирает
O(n) storage-чтение из горячего per-call пути полностью, оставляя лишь O(1) обращение к in-memory
словарю — как и было явно задумано для `last_call_cost_by_op`, просто не доведено до полной суммы.

### 4. [High] `PostgresStorage.prefetch_resume_cache()` — полный скан без поддерживающего индекса, растущий без ограничения по мере накопления истории

**File:Line**: индексы — `src/llm_bench/storage/postgres.py:108-110`; запрос —
`src/llm_bench/storage/postgres.py:260-287` (WHERE-условие на строках 269-274)

**Описание**: `_ddl()` создаёт ровно три индекса на `benchmark_results`:

```python
CREATE INDEX ... idx_benchmark_results_tag  ON {s}.benchmark_results (experiment_tag);   # 108
CREATE INDEX ... idx_benchmark_results_stage ON {s}.benchmark_results (stage);            # 109
CREATE INDEX ... idx_benchmark_results_task_unit ON {s}.benchmark_results (task_unit_id); # 110
```

А `prefetch_resume_cache()` — вызывается **один раз при старте каждого прогона**
(`Benchmark.initialize()` → `ResumeCache.populate_from_storage()` → `storage.prefetch_resume_cache()`,
`benchmark.py:107-108`, `resume.py:45-60`) — выполняет:

```sql
SELECT composite_hash, provider, model, thinking, response, ...
FROM {schema}.benchmark_results
WHERE response IS NOT NULL AND length(response) >= $1
  [AND (error_class IS NULL OR error_class = '')]
```

— **без фильтра по `experiment_tag`** (намеренно, кэш tag-agnostic по конструкции — docstring
`storage/base.py:79-89` явно это описывает как фичу: "reusable as a cache hit by a run under any other
tag"), и без фильтра по `stage`/`task_unit_id`. То есть ни один из трёх существующих индексов
**не покрывает ни одного столбца**, реально участвующего в этом WHERE (`response`, `length(response)`,
`error_class`) — Postgres вынужден делать полный последовательный скан всей таблицы
`benchmark_results` при каждом старте каждого прогона.

**Why it matters / сценарий отказа**: Поскольку это происходит на **каждом** запуске (это первый шаг
`initialize()`, блокирующий начало round 1), а таблица по своей природе накапливает строки от **всех**
когда-либо выполненных прогонов (resume-кэш tag-agnostic специально для этого), время старта каждого
нового benchmark-прогона будет линейно расти вместе с суммарной историей использования инструмента —
чем успешнее инструмент прижился (больше прогонов в истории), тем медленнее стартует каждый следующий.
Это ровно тот сценарий, о котором явно предупреждает докстринг `FileStorage` (файловый бэкенд честно
документирует "fast enough to ~50K rows; switch to PG beyond that", `file.py:23`) — но у `PostgresStorage`
аналогичного предупреждения нет, хотя её собственный "рекомендованный для больших объёмов" путь имеет
такую же незакрытую дыру по индексам для этого конкретного запроса.

**Recommendation**: Добавить частичный (partial) индекс, реально покрывающий этот запрос, например:
`CREATE INDEX ... ON benchmark_results (composite_hash, provider, model, thinking) WHERE error_class IS
NULL AND response IS NOT NULL` (partial index заодно решает проблему с "успешные" — самый частый вызов
идёт с `only_successful=True`). Для варианта без фильтра по `error_class` можно дополнительно завести
обычный B-tree по `(composite_hash, provider, model, thinking)` — этот PK и так есть на
`benchmark_results` (строка 105: `PRIMARY KEY (composite_hash, provider, model, thinking)`), но сам PK
не помогает конкретно этому запросу, поскольку тут нет равенства ни по одному из PK-столбцов — фильтрация
идёт по `response`/`error_class`, а не по identity-полям.

`Benchmark` по умолчанию допускает до 30 одновременных (model, task_unit)-пайплайнов

итерации, а не отпускает сразу) реальное время удержания соединения не всегда тривиально, и
рассинхрон "8 против 30" — это конкретная, легко устранимая асимметрия конфигурации, а не
теоретический риск.

**Recommendation**: Поднять дефолт `max_connections` минимум до уровня `global_concurrency` (или
явно задокументировать в докстринге `Benchmark`/`PostgresStorage`, что оператор обязан согласовывать
эти два числа вручную) — благо оба значения свободно настраиваются на конструкторах.

### 6. [Medium] `FileStorage.query_rows(stage=...)` не спускает фильтр по стадии на уровень чтения файла

**File:Line**: `src/llm_bench/storage/file.py:236-269`, конкретно фильтр на строке 256:
`if stage is not None and row.stage != stage: continue`

**Описание**: Метод принимает опциональный параметр `stage`, но применяет его **после** того, как
каждая строка файла уже прочитана и распарсена через `orjson.loads` (строка 252) и превращена в
`RunRow` (`_dict_to_row`, строка 255) — то есть I/O и CPU-парсинг всего файла происходят независимо от
того, нужна ли вызывающему коду одна стадия или все. Единственный публичный вызов с непустым `stage=`
внутри этого репозитория — мёртвый `load_winner_substrate` (см. Info-находку ниже); текущие живые
вызовы (`compute_ranking`, `query_spend_total`, `query_spend_by_stage`, `query_spend_by_op`) всё равно
идут без фильтра по стадии, так что для них разница нулевая — но контракт метода (сигнатура принимает
`stage`) обещает эффективную фильтрацию, которой на деле нет.

**Why it matters**: Основная практическая цена этой находки — не самостоятельная, а как множитель
находок #1 и #3: каждый факт "нужно перечитать файл" (там, где он всё равно уже нужен целиком) не
усугубляется, но если/когда в проекте появится вызывающий код, рассчитывающий получить только строки
одной стадии из большого лога, он неожиданно получит стоимость полного файла вместо ожидаемой
пропорциональной экономии.

**Recommendation**: Либо честно задокументировать в докстринге метода, что `stage=` — это post-hoc
фильтр без I/O-экономии (соответствует Protocol-докстрингу `storage/base.py:100-113`, который тоже не
обещает I/O-эффективность), либо — если `stage` действительно предполагался как way, чтобы не читать
весь файл, — завести отдельный индекс/шардирование по стадии (например, отдельный jsonl на стадию
внутри директории тега) для реального ускорения.

### 7. [Medium] `FileStorage` сериализует ВСЕ операции одним `asyncio.Lock`, включая полные сканы файла

**File:Line**: `src/llm_bench/storage/file.py:74` (`self._lock = asyncio.Lock()`), захваты — `138`
(`record_call`), `186` (`prefetch_resume_cache`), `245` (`query_rows`), косвенно также `287-294`
(`query_spend_by_op` идёт через `query_rows`)

**Описание**: Единственный `asyncio.Lock` на весь экземпляр `FileStorage` защищает и быстрые точечные
операции (SQLite PK-проверка перед вставкой, `file.py:141-146`), и потенциально долгие операции
полного скана файла (`query_rows`, строки 245-267 — читает файл целиком **под локом**, лишь потом
отдаёт строки итератором **вне** лока, строки 268-269 — это в целом хороший паттерн "не держи лок во
время выдачи вызывающему", но сам скан всё равно идёт под локом). Пока один concurrent-таск держит
лок ради полного скана, все остальные конкурентные таски, которым нужно всего лишь вставить одну
строку (`record_call`), вынуждены ждать в очереди на тот же лок.

**Why it matters**: Отдельно от находки #3 (где это уже подтверждено измерением), это общий
архитектурный риск: любой будущий код, который дергает `query_rows`/`prefetch_resume_cache`/
`query_spend_*` в разгар конкурентного раунда (а не строго на барьере между раундами, как сейчас
`compute_ranking`), автоматически сериализует весь параллелизм `global_concurrency` до momentar
однопоточного I/O. Это не баг сам по себе (лок нужен для корректности при конкурентной записи в один
файл), но выбор гранулярности — один общий лок на всё, а не отдельные локи для "быстрых точечных
операций" и "медленных полных сканов" — делает любую будущую или существующую (см. #3) дорогую
read-операцию потенциальным throughput-убийцей.

**Recommendation**: Разделить лок минимум на два (например, `_write_lock` для append/record_call и
`_scan_lock` — или `asyncio.Lock` вокруг только доступа к SQLite-индексу, отдельно от блокировки на
время чтения `results.jsonl`), либо переложить полные сканы на снапшот-чтение файла вне лока (файл уже
пишется атомарно через append — читать "грязный хвост" не хуже, чем текущее поведение с диапазоном
консистентности на весь файл).

**Описание**: `_run_pipeline()` вызывает `await cfg.storage.upsert_prompts(system_text=sys_p,

`composite_hash` — тривиальный O(1)-чек вместо гарантированного no-op запроса к storage.

### 10. [Low] `InMemoryStorage.query_rows`/`load_winners` — `deepcopy` вместо более дешёвой изоляции

**File:Line**: `src/llm_bench/storage/memory.py:137` (`query_rows`), `188` (`load_winners`)

**Описание**: `query_rows` строит снапшот `[deepcopy(r) for r in self._rows.values() if ...]` под
локом (строка 137); `load_winners` делает `deepcopy(ws)` (строка 188). `RunRow` — изменяемый

**Why it matters**: `InMemoryStorage` — явно тестовый/smoke бэкенд ("NEVER for production: data is

(чтобы вызывающий код не мог случайно мутировать внутреннее состояние стораджа через возвращённый

пересчитано на каждый вызов") и стоит недорогого исправления, если этот бэкенд когда-нибудь начнут

hypothesis).

**Recommendation**: Для `RunRow` (обычный dataclass) достаточно `dataclasses.replace(r)` — это
поверхностная копия верхнего уровня датакласса, которая всё ещё защищает от переприсваивания полей
вызывающим кодом (главный практический риск), просто не клонирует рекурсивно вложенные списки/словари,
которые в реальности после записи строки уже не мутируются раннером.

### 11. [Info] `load_winner_substrate` не подключена к `round_runner.py` — при подключении её текущая реализация станет N+1

**File:Line**: `src/llm_bench/ranking/per_stage_winners.py:81-114`

**Описание**: Докстринг модуля (`per_stage_winners.py:1-18`) и докстринг самой функции
(строки 94-99: "The round driver invokes this BEFORE building any candidate's prompt for stage k+1...
Without this wiring, 'M_X promotion' is write-only and stage k+1 silently uses each candidate's own

следующей стадии. Однако `grep` по всему `src/` и `examples/` показывает, что `load_winner_substrate`
не вызывается **нигде**, кроме собственного определения и публичного ре-экспорта

`benchmark.py` её не используют. Это прежде всего корректностная находка (вероятно, покрыта другим
аудит-лейном), но у неё есть и прямое отношение к производительности: реализация функции
(`per_stage_winners.py:105-107`) делает


— то есть тянет **все** строки данной стадии (см. также находку #6 — `stage=` не экономит I/O для

AND task_unit_id=$4 ORDER BY ts DESC LIMIT 1`, для File — прямой SQLite-индекс лукап вместо скана
JSONL), либо предзагружать все winner-substrate строки одним batched-запросом в начале раунда (по
